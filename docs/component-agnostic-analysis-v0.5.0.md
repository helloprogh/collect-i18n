# 组件库无关采集方案分析（v0.5.0）

> 结论先行：**有，而且 v0.5.0 已经把它落地了**。核心思路是把采集点从「组件库的最终渲染产物」上移到「vue-i18n 的 t() 值层」——这是所有渲染路径（DOM 文本、canvas 轴标签、瞬态 toast、命令式弹窗）唯一共同经过的漏斗。在这个漏斗上做证据镜像 + 通用 ARIA 交互配方，就不需要为任何组件库写适配。

## 1. 为什么过去看起来「必须适配组件库」

v0.4.0 目标项目分析暴露的三类顽固场景，表面看都要求组件库知识：

| 场景 | 为什么难 | 组件库适配思路 | 代价 |
| --- | --- | --- | --- |
| 瞬态消息（ElMessage 1.5s 消失） | 元素挂载时间太短，常规 inspect 错过 | 点击后 300ms 内抓 .el-message | 换库（AntD/Naive）就要重写选择器 |
| 下拉/悬浮菜单 | 未展开时元素不在 DOM | 点 .el-dropdown 再抓 .el-dropdown-menu | 同上；每个库的触发类名都不同 |
| 画布文本（ECharts） | 文本画在 canvas 上，没有 DOM 节点 | 拿 echarts.getInstanceByDom().getOption() | 只对 ECharts 有效；拿不到实例就无解 |
| 动态拼接键 | 源里是 t("products.rows." + x + ".category")，静态扫描只有前缀 | 无 | 只能等运行时实例化 |

这些适配都建立在同一个假设上：**必须从组件库的渲染产物里取证**。但有一个更早的观察点可以绕开全部组件库知识。

## 2. 组件库无关方案：在 t() 值层取证（已实现）

### 2.1 运行时证据镜像（镜像条）

我们自己的插桩本来就包裹了每一个 i18n 表达式（recordRenderedValue）。在 v0.5.0 里，当任意 t() 值流经时（无论最终渲染到 DOM、canvas 还是瞬态 toast），runtime 把「key → 渲染文本」追加进一个离屏镜像条：

- **不依赖组件库**：镜像不认识 .el-message、.ant-btn，只认识 t() 的返回值；
- **覆盖画布 formatter**：ECharts 的 axis/legend formatter 在渲染时调用 t()，值层必然被记录，无需 getOption()，无需知道图表库名称；
- **覆盖瞬态消息**：ElMessage.success(t(...)) 走命令式调用，同样经过 t()；文本在镜像里是持久记录，不再需要 300ms 抢拍 DOM；
- **覆盖动态键**：t("products.rows." + x + ".category") 在运行时解析出完整实例键 products.rows.3.category，镜像以真实键记录；
- **证据质量**：截图的就是应用自己用 t() 渲染出的中文文本（在镜像条视口中），标 B 级（proof runtime-mirror），与「应用内部文本」证据语义一致；镜像只在对焦截图时临时可见，不影响任何正常页面截图。

### 2.2 通用 ARIA 交互配方（R8）

需要「点击才能挂载」的内容（未展开 tab 面板、悬浮菜单、按钮触发的弹窗），用组件无关的交互扫描：

- 目标 = [role=tab] → 原生 button / [role=button]（ARIA 语义，三大组件库全部遵循）；
- 每轮点 1 个未扫目标 → 等瞬态内容 → 批量截图 → Escape 收尾；有界 ≤10 轮/路由；
- 触发后哪怕是瞬态内容，其 t() 值也已进镜像；两者叠加，连 EP 特有的悬浮菜单都不需要 .el-dropdown 选择器。

### 2.3 兜底仍是通用机制

- **动态键转正**：静态阶段标 needs_manual 的键，运行时一旦真实实例化（DOM 或镜像）就自动升格为 captured；死键永远不会实例化，自然留在人工队列。这与组件库完全无关。
- **其余人工队列**：继续按「动态拼接未实例化 / 画布在无 t() 路径 / 死键」细分原因（manualReason + Excel 标注），评审批量处理。

## 3. 还有哪些场景本质上需要组件库知识（诚实边界）

镜像在 t() 值层取证，理论上覆盖「任何组件库渲染」的文本。剩余边角：

1. **不经过 t() 的文本**：组件从 JSON/后端直接取文案、或硬编码在组件库内部（如日期面板的星期标题如果走组件库内置 i18n 而非项目 vue-i18n）——这些本来就不是本工具的采集对象（四列工作簿只覆盖项目 locale 文件）；
2. **组件库内部的 i18n 桥**（如 Element Plus 的 el-config-provider locale）如果项目用它承载业务词条，值层仍会流经 t()——被镜像覆盖；若不流经，则不属于目标词条；
3. **需要「操作某个具体控件形态」才能触达的深交互**（如穿梭框转移按钮）——R8 的通用点击可能点到；点不到就进 Agent 计划（TriggerPlan 由 Agent 按源证据生成，本身就允许写具体选择器；这不是组件库适配，是场景级的手工计划）。

## 4. 方案矩阵对比

| 方案 | 组件库专属程度 | 弹性/复杂度 | 自动化率收益 | 落地状态 |
| --- | --- | --- | --- | --- |
| 组件库配方库（.el-message 等） | 高 | 每个库一套，维护重 | 高但脆 | v0.4 思路 → 已被替代 |
| ARIA 通用交互扫描 | 低 | 一套通吃 | 中（配合镜像抬高到高） | v0.5.0 R8 |
| t() 值层证据镜像 | 无 | 一行插桩钩子 | 高且稳（覆盖画布/瞬态/动态） | v0.5.0 R9（核心） |
| TriggerPlan 手工计划 | 无（场景级选择器） | Agent 按需生成 | 兜底 | 既有 |

## 5. 结论

有方案不用适配组件库，且已在 v0.5.0 双通道落地：**证据镜像在 t() 值层取证（覆盖画布/瞬态/动态），ARIA 通用交互扫描负责「点开才挂载」的内容**。组件库专属选择器从采集引擎的确定性路径里彻底消失了——剩下的具体选择器只出现在 Agent 手工计划里，那是「具体场景配方」而不是「库适配」。后续换库（EP→AntD→Naive）或目标项目混用多库，采集引擎不用改一行。
